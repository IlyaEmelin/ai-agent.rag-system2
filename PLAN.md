- Для каждой версии сохранить метаданные:
  - `doc_id`;
  - `title`;

- Построить эмбеддинги моделью `intfloat/multilingual-e5-base`.

- Посчитать retrieval-метрики без `gap`-запросов:
  - `precision@5`;
  - `recall@5`;
  - `MRR`;
  - `recall@K` для `K = {1, 3, 5, 10, 20}`.
- Просмотреть несколько чанков вручную: не разорваны ли факты и сохраняется ли смысл.
- Выбрать стратегию чанкинга по метрикам и примерам.

Результат: выбранная стратегия чанкинга и baseline dense retrieval.

## Шаг 4. Собрать baseline retrieval и провести диагностику

- Настроить итоговый FAISS retrieval на выбранных чанках.
- Подобрать порог отсечения по распределению сходств.
- Реализовать выдачу top-K чанков с метаданными.
- Проверить, не занижается ли `recall@K` из-за того, что FAISS возвращает top-K чанков, а метрики считаются по уникальным `doc_id`:
  - получить расширенный список top-50/top-100 chunk-кандидатов;
  - агрегировать чанки в уникальные документы по лучшему score;
  - сравнить метрики chunk-level baseline и doc-level overfetch baseline.
- Показать пример фильтрации по категории `Подписка и оплата`.
- Найти запросы с низкими метриками.
- Посчитать диагностику отдельно по типам запросов:
  - `exact`;
  - `semantic`;
  - `multi`.
- Диагностировать причины ошибок:
  - нужный документ ниже top-5;
  - нужный документ отсутствует даже в top-20/top-100 candidate pool;
  - сильная переформулировка запроса;
  - точные термины/коды плохо находятся dense-поиском;
  - multi-запрос объединяет несколько независимых фактов и требует декомпозиции;
  - проблема в чанкинге или очистке.

## Шаг 5. Улучшить retrieval и выбрать итоговую схему поиска

Цель: повысить полноту retrieval. Так как baseline `recall@20` ниже желаемого уровня, сначала улучшается candidate generation, а reranker подключается только после проверки, что нужные документы попадают в расширенный candidate pool.

- Улучшить searchable text для retrieval:
  - включить в текст для индексации заголовок;
  - включить категорию;
  - сохранить исходный `page_content` отдельно для показа пользователю и передачи в LLM.
- Реализовать dense retrieval с overfetch:
  - получать top-50/top-100 чанков;
  - агрегировать результаты в уникальные `doc_id`;
  - выбирать top-K документов по лучшему score чанка.
- Добавить BM25 по чанкам.
- Объединить dense FAISS и BM25 через RRF.
- Для `semantic`-запросов попробовать query expansion.
- Для `multi`-запросов попробовать query decomposition:
  - исходный запрос;
  - подзапросы;
  - объединение результатов через RRF.
- Опционально попробовать HyDE и оставить его только если он улучшает метрики на том же evaluation-наборе.
- Сравнить варианты на одних и тех же retrieval-метриках:
  - dense baseline;
  - dense overfetch + doc aggregation;
  - BM25;
  - dense + BM25 RRF;
  - RRF + query expansion/decomposition;
  - RRF + HyDE, если применимо.
- Если после baseline/RRF и трансформаций запроса `recall@5` ниже ориентира, а нужные документы есть в top-20/top-50/top-100, но плохо ранжируются, подключить cross-encoder reranker.
- Зафиксировать цену улучшений:
  - задержка;
  - дополнительная модель;
  - сложность пайплайна.
- Выбрать итоговую схему retrieval.

Результат: улучшенный retrieval с сравнением `до → после` и объяснением, какие ошибки baseline исправлены.
