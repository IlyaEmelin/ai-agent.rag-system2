# PLAN.md

## План реализации RAG-проекта «Фильмоскоп»

Цель плана — реализовать проект минималистично в одном Jupyter Notebook, строго по требованиям задания и текущей спецификации `spec.md`.

## Шаг 1. Подготовить окружение и базовую структуру ноутбука

- Создать основной Jupyter Notebook с шестью разделами по этапам задания.
- Проверить доступность датасета `filmoskop_kb.json`.
- Проверить локальный LLM endpoint:
  - `http://localhost:8080/v1/models`;
  - модель `unsloth/Qwen3.5-4B-GGUF:Q4_K_M`.
- Проверить FAISS GPU на целевой машине:
  - `import faiss`;
  - `hasattr(faiss, "StandardGpuResources")`;
  - `faiss.get_num_gpus() > 0`.
- Зафиксировать seed, константы путей, модель эмбеддингов `intfloat/multilingual-e5-base`, top-K и фразу отказа.

Результат: ноутбук запускается, зависимости и внешние точки входа проверены.

## Шаг 2. Выполнить аудит и очистку корпуса

- Загрузить `docs` и `queries` из JSON.
- Посчитать базовую статистику:
  - число документов и запросов;
  - категории;
  - форматы;
  - длины текстов;
  - типы запросов.
- Найти проблемы простыми эвристиками:
  - остатки HTML/markdown;
  - подозрительно короткие и длинные документы;
  - дубли;
  - аномальные символы/mojibake.
- Очистить документы:
  - `trafilatura` для HTML;
  - простая очистка markdown/text;
  - `ftfy` при необходимости;
  - нормализация пробелов.
- Показать примеры `было → стало`.

Результат: очищенный корпус с кратким выводом по качеству данных.

## Шаг 3. Сравнить две стратегии чанкинга и выбрать одну

- Построить две версии чанков через `RecursiveCharacterTextSplitter`:
  - маленькие чанки;
  - средние чанки.
- Для каждой версии сохранить метаданные:
  - `doc_id`;
  - `title`;
  - `category`;
  - `chunk_id`.
- Построить эмбеддинги моделью `intfloat/multilingual-e5-base`.
- Собрать FAISS GPU индекс для каждой стратегии.
- Посчитать retrieval-метрики без `gap`-запросов:
  - `precision@5`;
  - `recall@5`;
  - `MRR`;
  - `recall@K` для `K = {1, 3, 5, 10, 20}`.
- Просмотреть несколько чанков вручную: не разорваны ли факты и сохраняется ли смысл.
- Выбрать стратегию чанкинга по метрикам и примерам.

Результат: выбранная стратегия чанкинга и baseline dense retrieval.

## Шаг 4. Собрать baseline retrieval и провести диагностику

- Настроить итоговый FAISS retrieval на выбранных чанках.
- Подобрать порог отсечения по распределению сходств.
- Реализовать выдачу top-K чанков с метаданными.
- Показать пример фильтрации по категории `Подписка и оплата`.
- Найти запросы с низкими метриками.
- Диагностировать причины ошибок:
  - нужный документ ниже top-5;
  - сильная переформулировка запроса;
  - точные термины/коды плохо находятся dense-поиском;
  - проблема в чанкинге или очистке.

Результат: baseline-метрики, список проблемных запросов и диагнозы.

## Шаг 5. Улучшить retrieval и выбрать итоговую схему поиска

- Добавить BM25 по чанкам.
- Объединить dense FAISS и BM25 через RRF.
- Для semantic/multi-запросов попробовать оба подхода:
  - query expansion;
  - HyDE.
- Сравнить варианты на одних и тех же retrieval-метриках.
- Если после baseline/RRF и трансформаций запроса `recall@5` ниже ориентира или нужные документы есть в top-20, но плохо ранжируются, подключить cross-encoder reranker.
- Зафиксировать цену улучшений:
  - задержка;
  - дополнительная модель;
  - сложность пайплайна.
- Выбрать итоговую схему retrieval.

Результат: улучшенный retrieval с сравнением `до → после`.

## Шаг 6. Собрать генерацию ответов и LLM-судью

- Собрать полный RAG pipeline:
  - вопрос;
  - итоговый retrieval;
  - формирование контекста;
  - prompt;
  - генерация ответа.
- Использовать локальный OpenAI-compatible endpoint `http://localhost:8080/` и `temperature=0`.
- В prompt явно запретить отвечать вне контекста.
- Для недостаточного контекста возвращать единую фразу отказа.
- Проверить примеры разных типов запросов, включая `gap`.
- Реализовать LLM-судью для:
  - faithfulness;
  - answer relevance;
  - correctness.

Результат: система отвечает по контексту, отказывается при отсутствии данных и умеет оценивать ответы.
