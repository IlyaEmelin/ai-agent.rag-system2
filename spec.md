# RAG-ассистент поддержки онлайн-кинотеатра «Фильмоскоп»

## 1. Назначение проекта

Проект спринта 2 — воспроизводимый Jupyter Notebook с полноценной RAG-системой для службы поддержки онлайн-кинотеатра «Фильмоскоп».

Бизнес-задача: разработать прототип ассистента, который отвечает на вопросы пользователей по действующей базе знаний, честно отказывается отвечать при отсутствии сведений и имеет измеримое качество, подтверждённое метриками, диагностикой ошибок и инженерным вердиктом.

Формальная задача: собрать и оценить полный RAG-пайплайн:

```text
подготовка корпуса → чанкинг → эмбеддинги → векторная база → retrieval и его улучшение → генерация → оценка качества и диагностика
```

Главный артефакт — выполненный notebook `filmoskop_rag.ipynb`, который запускается сверху вниз без ручных изменений между ячейками и содержит сохранённые outputs.

## 2. Целевые ориентиры

Система считается готовой к учебному пилоту, если на тестовом наборе:

- `recall@5 >= 0.85` для итогового поиска по запросам, ответ на которые есть в базе;
- `correctness >= 0.90` по всем 66 тестовым запросам;
- на `gap`-запросах система не выдумывает факты и возвращает согласованную фразу отказа.

Если итоговая метрика немного ниже ориентира, но pipeline выполнен полностью, а причины потерь разобраны, это тоже инженерный результат. Высокая метрика без воспроизводимой процедуры и анализа ошибок недостаточна.

Тестовый набор малый: 66 запросов помогают диагностировать крупные эффекты, но не дают права делать сильные статистические утверждения о небольших различиях между методами. В выводах нужны аккуратные формулировки: профиль по типам запросов, конкретные ошибки и ограничения — да; уверенное утверждение о преимуществе на несколько процентных пунктов без дополнительной проверки — нет.

## 5. Требования по этапам

### Этап 1. Аудит и подготовка корпуса

Нужно загрузить датасет и изучить корпус: количество разделов и запросов, категории, форматы, длины текстов, распределение типов запросов.

Нужно найти проблемы качества данных вручную и простыми эвристиками:

- доля мусорных символов;
- остатки HTML/markdown-разметки;
- HTML entities;
- mojibake;
- zero-width symbols;
- переносы через дефис;
- гомоглифы;
- подозрительно короткие и длинные документы;
- заглушки;
- архивные/устаревшие статьи;
- точные и почти точные дубли.

Нужно собрать процедуру очистки и нормализации: `ftfy` для mojibake, `trafilatura` или эквивалент для HTML, регулярные выражения для markdown/text, Unicode-нормализация, нормализация пробелов, удаление zero-width symbols, безопасная склейка переносов через дефис, безопасное исправление гомоглифов.

Нужно явно разделить:

- документы, которые удалось восстановить и оставить;
- документы, которые фильтруются из retrieval-index;
- документы с невосстановимой потерей данных.

Из retrieval-index нужно исключить заглушки, архивные/устаревшие статьи, слишком короткие неинформативные разделы, дубли и near-duplicates. Для исключённых документов нужна таблица: `doc_id`, `title`, `reason`, длина после очистки, `kept_doc_id` для дублей.

Важно: не удалять данные, которые можно восстановить. Если данные потеряны в источнике, например из-за символов замены Unicode, это нужно явно отметить как ограничение.

### Этап 2. Чанкинг и эмбеддинги

Нужно выбрать минимум две стратегии чанкинга и применить обе к индексируемому корпусу.

Для каждого чанка нужно сохранить метаданные: `doc_id`, `title`, `category`, `chunk_id`, позиция/номер чанка внутри документа.

Эмбеддинги строятся моделью `intfloat/multilingual-e5-base` из `sentence-transformers`. Для e5 обязательны префиксы:

- `query: ` для запросов;
- `passage: ` для документов/чанков.

Векторы нужно нормализовать, если используется cosine-подобный поиск через inner product.

Стратегии сравниваются по retrieval-метрикам на одних и тех же non-gap запросах. Числа нужно дополнить ручным просмотром чанков: не разорваны ли факты, не потерялось ли подлежащее, сохраняется ли смысл без соседних фрагментов.

### Этап 3. Поисковая инфраструктура и retrieval

Нужно выбрать векторное хранилище и обосновать выбор. По умолчанию используется FAISS `IndexFlatIP`:

- корпус маленький, поэтому точный поиск допустим;
- нормализованные эмбеддинги + inner product эквивалентны cosine similarity;
- FAISS CPU достаточно для локального запуска;
- при существенном росте корпуса решение нужно пересмотреть в сторону ANN/шардирования/отдельной vector DB.

Retrieval pipeline:

```text
query → query embedding → vector search → threshold diagnostics → top-K chunks with metadata → unique doc_id for metrics
```

Нужно подобрать порог по распределению сходств и объяснить, используется ли он в финальном pipeline. Если порог остаётся только диагностическим, нужно явно сказать почему: например, малый eval-набор и риск ухудшить recall.

Нужно показать пример фильтрации по метаданным, например только по категории `Подписка и оплата`.

Baseline retrieval-метрики считаются только по запросам с ответом в базе, без `gap`:

- `precision@5`;
- `recall@5`;
- `MRR`;
- `recall@K` для `K = {1, 3, 5, 10, 20}`.

Так как разметка дана по разделам, а поиск возвращает чанки, метрики считаются по уникальным `doc_id`, полученным из top-K чанков.

### Этап 4. Диагноз и улучшение retrieval

Нужно найти запросы с низкими метриками и поставить диагноз:

- нужный документ есть в top-20/top-100, но ниже top-5;
- формулировка запроса сильно отличается от текста документа;
- exact-термины и коды плохо обрабатываются dense-поиском;
- проблема связана с чанкингом;
- проблема связана с грязными или устаревшими данными.

Методы улучшения выбираются по диагнозу. Допустимые методы: cross-encoder reranker, BM25, hybrid search, RRF, query expansion, HyDE, coverage-aware selection для `multi`.

Нужно сравнить `до → после` на тех же запросах и метриках. Итоговые числа должны относиться именно к финальной выбранной схеме, а не к промежуточному эксперименту.

Нужно оценить цену улучшения: задержку, дополнительную модель, вычислительные ресурсы, сложность pipeline. Если эвристики подбирались на этих же 56 non-gap запросах, это нужно честно назвать tuning on eval set / подгонкой под диагностический набор.

### Этап 5. Генерация ответов

Нужно собрать полный RAG pipeline:

```text
вопрос → retrieval → контекст → prompt → генерация ответа
```

Требования:

- локальный OpenAI-compatible endpoint допустим;
- `temperature=0`;
- контекст и вопрос явно разделены;
- генератор получает найденный контекст, а не весь корпус;
- если контекста недостаточно, возвращается фиксированная фраза отказа: `В базе знаний нет информации для ответа на этот вопрос.`

Нужно проверить примеры всех типов запросов, включая `gap`. Финальная оценка выполняется на всех 66 запросах на этапе 6.

### Этап 6. Оценка качества и диагностика

Нужно прогнать все 66 запросов через итоговый pipeline и сохранить для каждой строки: `idx`, `query`, `kind`, `gold`, `relevant_docs`, найденные `doc_id` и заголовки, контекст, ответ, retrieval flags, faithfulness score, answer relevance score, correctness, judge reason, `judge_parse_ok`, `judge_fallback_used`, время выполнения.

Retrieval-метрики считаются без `gap`; generation-метрики считаются по всем 66 запросам.

LLM-судья должен оценивать:

- `faithfulness` — насколько ответ опирается на найденный контекст, шкала 1–5;
- `answer_relevance` — отвечает ли ответ на вопрос, шкала 1–5;
- `correctness` — бинарная сверка с `gold`, значение 0/1.

Для шкал 1–5 нужно считать средний score, долю строк со score `>= 4` и разбивку по типам запросов. Строки, где сработал fallback judge, нужно отделить от основного профиля или явно показать отдельным счётчиком.

Нужно выполнить golden-context run: передать генератору размеченные `relevant_docs` вместо найденных retrieval-контекстов и сравнить `correctness`. Это показывает, сколько качества теряется на поиске, а сколько на генерации.

Нужно вручную разобрать худшие ошибки: retrieval misses, generation misses при найденном правильном контексте, ошибки `multi`, проблемные `gap`, parse failures judge.

Финальный вывод должен содержать: достигнуты ли целевые ориентиры, готова ли система к пилоту, три конкретные рекомендации по улучшению и зачем они нужны.

Answer relevance prompt:

```python
RELEVANCE_PROMPT = """Оцени РЕЛЕВАНТНОСТЬ ОТВЕТА ВОПРОСУ (answer relevance):
насколько ответ отвечает именно на заданный вопрос пользователя.
```

Correctness prompt должен сравнивать ответ с `gold` и возвращать бинарный score: `0` или `1`.

Для `gap` корректным считается отсутствие выдуманных фактов и согласованный отказ. Если требуется строгий exact match фразы отказа, это нужно проверять отдельной deterministic-проверкой.

## 7. Оформление и воспроизводимость

Требования к сдаче:

- notebook разделён на шесть этапов задания;
- код выполняется сверху вниз без ручных изменений;

- случайность фиксируется через seed;
- `temperature=0` для языковой модели;
