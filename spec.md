# RAG-ассистент поддержки онлайн-кинотеатра «Фильмоскоп»

## Краткое описание

Проект — воспроизводимый Jupyter Notebook с компактной RAG-системой для ответов на вопросы пользователей онлайн-кинотеатра «Фильмоскоп» по базе знаний `filmoskop_kb.json`.

Система должна:

- очищать сырые документы базы знаний;
- разбивать корпус на чанки;
- строить dense-поиск по FAISS;
- улучшать retrieval на основе диагностики;
- генерировать ответы строго по найденному контексту;
- честно отказываться, если ответа в базе нет;
- считать метрики retrieval и генерации;
- содержать краткий инженерный вывод о готовности к пилоту.

Главный принцип реализации: минимальный объём кода, без проверок, абстракций и дополнительных компонентов, которые прямо не требуются заданием.

## Проблема и цель

### Проблема

Обычная языковая модель без базы знаний может выдумывать тарифы, акции и инструкции поддержки. Для службы поддержки это неприемлемо: ответы должны опираться на действующую базу знаний.

### Цель

Собрать прототип RAG-ассистента, который отвечает на вопросы по базе знаний «Фильмоскопа», отказывается при отсутствии данных и имеет измеримое качество.

Целевые ориентиры из задания:

- `recall@5 >= 0.85` для итогового поиска по запросам с ответом в базе;
- `correctness >= 0.90` по всему тестовому набору;
- для `gap`-запросов система возвращает согласованную фразу отказа и не выдумывает факты.

## Пользователи и роли

- Пользователь онлайн-кинотеатра: задаёт вопрос о подписке, оплате, устройствах, ошибках, аккаунте, профилях, функциях или контенте.
- Оператор или инженер поддержки: использует прототип для проверки качества RAG-подхода.
- Ревьюер проекта: воспроизводит ноутбук, проверяет логику решений, метрики и выводы.

## Основные сценарии

1. Пользователь задаёт вопрос, ответ на который есть в базе знаний.
2. Система находит релевантные чанки, формирует контекст и генерирует короткий ответ по контексту.
3. Пользователь задаёт вопрос, ответа на который нет в базе.
4. Система возвращает единую фразу отказа без выдуманных фактов.
5. Инженер запускает ноутбук сверху вниз и получает:
   - очищенный корпус;
   - сравнение стратегий чанкинга;
   - baseline retrieval;
   - улучшенный retrieval;
   - ответы генератора;
   - метрики и диагностику ошибок.

## Объём первой версии (MVP)

- Retrieval с top-K чанками, метаданными и порогом отсечения по распределению сходств.
- Один пример фильтрации по категории `Подписка и оплата`.
- Генерация ответа через локальный OpenAI-compatible LLM endpoint `http://localhost:8080/` с `temperature=0`.
- Единая фраза отказа для вопросов без ответа.
- LLM-судья для:
  - faithfulness;
  - answer relevance;
  - correctness.
- Прогон всех 66 запросов.
- Прогон с золотым контекстом.
- Итоговый профиль качества, разбор ошибок, вердикт и 3 рекомендации.

### Не входит в MVP

- Отдельное Python-приложение, API, UI или CLI.
- Многофайловая архитектура, если всё помещается в один ноутбук.
- Chroma или Qdrant, если FAISS достаточно для малого корпуса.
- Сложная система логирования.
- Автоматические тесты вне ноутбука.
- Сложные проверки безопасности, не требуемые заданием.
- Миграции, Docker, orchestration, web-сервер.
- Сохранение индексов как обязательная часть, если построение индекса быстро выполняется в ноутбуке.
- Дополнительные метрики и эксперименты, кроме явно нужных для выбора решений и диагностики.

## Функциональные требования

1. Ноутбук должен загружать датасет и разделять его на `docs` и `queries`.
2. Ноутбук должен показывать базовую статистику корпуса:
   - число разделов;
   - число запросов;
   - распределение по категориям;
   - распределение по форматам;
   - распределение длин документов.
3. Ноутбук должен находить проблемы качества данных простыми эвристиками:
   - остатки HTML/markdown-разметки;
   - подозрительно короткие и длинные документы;
   - дубли или почти дубли;
   - аномальные символы или mojibake.
4. Ноутбук должен очищать корпус и показывать примеры `было → стало`.
5. Ноутбук должен построить две версии чанков и сравнить их retrieval-метрики на одном наборе запросов.
6. Поиск должен возвращать чанки с метаданными:
   - `doc_id`;
   - `title`;
   - `category`;
   - номер чанка.
7. Retrieval-метрики должны считаться по уникальным `doc_id`, полученным из top-K чанков.
8. `gap`-запросы не должны входить в retrieval-метрики.
9. Улучшенный retrieval должен сравниваться с baseline на тех же метриках.
10. Генератор должен получать вопрос и найденный контекст, а не весь корпус.
11. Если контекста недостаточно, генератор должен вернуть фиксированную фразу отказа.
12. Для всех 66 запросов должны быть сохранены ответы, найденные документы и оценки качества.
13. В конце каждого этапа должен быть краткий вывод:
    - что сделано;
    - что получено;
    - какое решение принято;
    - почему принято именно оно.

## Нефункциональные требования

- Ноутбук выполняется сверху вниз без ручного изменения ячеек.
- Код компактный и линейный, без лишних классов и инфраструктуры.
- Случайность фиксируется через seed, где это применимо.
- Для LLM используется `temperature=0`.
- Все решения должны быть обоснованы числами, примерами из данных или диагностикой.
- Выводы должны быть аккуратными: тестовый набор маленький, поэтому нельзя делать чрезмерно сильные статистические утверждения.
- Корпус малый: точный FAISS-поиск допустим; переход к ANN/компрессии рассматривается только как рекомендация для масштаба существенно больше текущего.

## Выбранная техническая реализация

Выбран вариант C: учебно-полный, но компактный RAG-пайплайн.

Состав:

1. Очистка корпуса:
   - `trafilatura` для HTML;
   - простая очистка markdown/text регулярными выражениями;
   - `ftfy.fix_text` при необходимости;
   - нормализация пробелов.
2. Чанкинг:
   - две стратегии `RecursiveCharacterTextSplitter`, например:
     - маленькие чанки: около 500 символов, overlap около 100;
     - средние чанки: около 900 символов, overlap около 150.
   - точные размеры финально выбираются по retrieval-метрикам и ручному просмотру.
3. Эмбеддинги:
   - `sentence-transformers`;
   - модель `intfloat/multilingual-e5-base`.
4. Векторная база:
   - FAISS GPU с поддержкой CUDA и точным поиском для малого корпуса.
5. Baseline retrieval:
   - dense-поиск по FAISS.
6. Улучшенный retrieval:
   - BM25 по чанкам;
   - RRF для объединения dense и BM25 результатов;
   - query expansion и HyDE для semantic/multi-запросов: пробуются оба варианта, затем выбирается лучший по метрикам;
   - reranker cross-encoder подключается, если после baseline/RRF и трансформаций запроса итоговый `recall@5` ниже ориентира или нужные документы есть в top-20, но плохо ранжируются.
7. Генерация:
   - OpenAI-compatible клиент к локальному LLM endpoint `http://localhost:8080/`;
   - модель `unsloth/Qwen3.5-4B-GGUF:Q4_K_M`;
   - `temperature=0`;
   - промпт с явным запретом отвечать вне контекста.
8. Оценка:
   - retrieval-метрики считаются кодом;
   - generation-метрики оцениваются LLM-судьёй;
   - дополнительно выводятся худшие примеры для ручного разбора.

## Ограничения и допущения

- Главный артефакт — один Jupyter Notebook.
- Проект намеренно не превращается в production-сервис.
- Все усложнения допускаются только если они прямо нужны для требований задания или объяснены диагностикой.
- FAISS GPU выбран как основной движок, потому что корпус маленький, не требует отдельного сервера векторной БД и будет выполняться в окружении с CUDA.
- BM25/RRF выбраны как компактный способ усилить exact-запросы и коды ошибок без тяжёлой инфраструктуры.
- FAISS GPU используем из уже установленного пакета в целевом окружении, если проверка `import faiss`, наличие `StandardGpuResources` и `faiss.get_num_gpus() > 0` проходит. В текущем локальном окружении `faiss` не установлен, поэтому окончательная проверка выполняется на целевой машине.
- Query expansion и HyDE используются как два сравниваемых способа улучшить semantic/multi-запросы; финальный вариант выбирается по retrieval-метрикам на одном и том же наборе запросов.
- Reranker не является обязательным компонентом baseline: он подключается по результатам диагностики, если после baseline/RRF и трансформаций запроса итоговый `recall@5` ниже ориентира или нужные документы есть в top-20, но плохо ранжируются.
- Для генерации и LLM-судьи используется локальный OpenAI-compatible endpoint `http://localhost:8080/`.
- Для исправления текстовых проблем используется `ftfy`; `charset-normalizer` не включается, потому что датасет уже читается как UTF-8 JSON, а работа с неизвестными байтовыми кодировками в MVP не требуется.
